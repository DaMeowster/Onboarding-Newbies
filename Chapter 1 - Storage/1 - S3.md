# Object Storage (S3-Compatible) – Client Perspective

Object storage systems expose a simple HTTP-based API for storing and retrieving data as objects.

From a client perspective, S3-compatible storage provides a unified way to interact with data regardless of the underlying implementation or vendor.

:warning: **Note:**  
This chapter is written strictly from the **client point of view**.  
We focus on how applications interact with the system not how it is implemented internally.  
We refer to **S3 and S3 compatible APIs**, for example using **Ceph** as interface.

# S3 Client Core Concepts

### ❓ Guide Questions

1. **Data Model, API, and Access Control:** Explain the flat namespace model of S3 (buckets, objects, keys, versions) and how it differs from a hierarchical file system. Explain why the namespace is flat rather than directory-based, what operations a client can perform using the S3 API, What are the different Storage Classes and compare how access is authorized at the client level using S3 API mechanisms (Bucket Policies, ACLs) versus user identities.
A:
במודל הnamespace  השטוח של S3 יש לנו כמה אובייקטים. האובייקט האחסון הכי גדול הוא bucket. בתוך הbuckets יש אובייקטים. למרות שיכול להראות בUI שיש היררכיה בתוך הbucket עם תיקיות שונות, אין באמת. כל האובייקטים נמצאים בתוך הbucket ואין באמת תת-תיקיות. לכל אובייקט יש key ייחודי שהמשתמש נותן לו שמזהה אותו. אם יש לי קובץ שיש לי כמה גרסאות שונות שלו שמורות, ניתן להשתמש בversions. זה יאפשר לנו שכל הקבצים האלו יהיו עם אותו מזהה מה שבדרך כלל אסור, ויהיה להם את המספר גרסה השונה שלפיו ניתן להבדיל. היתרון שאין היררכיה והכל שטוח בתוך הbucket נותן לנו גישות מאוד מהירות לאובייקט, במקום לעבור על היררכיה שלמה מוצאים אותו ישר לפי הid. בעזרת הS3 API ניתן לעשות את הפעולות PUT, GET, DELETE, LIST. בתוך S3 יש storage classes שונים. בגלל שמלכתחילה אנחנו יודעים שיש אזורים שנצטרך לגשת אליהם יותר מאחרים, ואנחנו רוצים לחסוך כסף, אז מתאימים ברמת הbucket או האובייקט storage class שמתאים לכמה אתה מצפה שתיגש אליו. אם אני אגש אליו הרבה וחשוב לי מהירות אז האחסון יעלה לי יותר, אם אני יודע שבקושי אגש וכשאני כן אין לי בעיה לחכות, אני יכול לחסוך כסף ולשלם על אחסון שמותאם לכך. יש את האופציה של bucket policies שמאפשרים גישה לbucket למשתמשים אחרים, הפורמט הוא קובץ json. יש אופציה לעשות את זה גם עם user identites, אבל יש כמה הבדלים. כשמדובר בbucket policy, הוא ספציפי לbucket אחד. ניתן להשתמש בidentity policy על כמה buckets שונים. כשמשכפלים bucket, אז הbucket policy משתכפל אבל אבל הidentity policy לא מתעדכן אוטומטית וצריך לשנות אותו ידנית. אם החוקים שלי הם מתאימים יותר לbucket כדאי ללכת עם הגישה של bucket policy, אבל אם זה יותר תלוי במשתמשים עצמם כנראה ששווה identity policy. 

2. **Durability, Distribution, and Failure Handling:** Explain how object stores achieve durability at scale through replication or erasure coding, how data and metadata are distributed across nodes, and how failures are detected and repaired. Why is distribution important for availability and resilience?
A:
מה שעוזר לשרידות גם במספרים עצומים של המידע זה שכפול וerasure coding. ניתן לשכפל את המידע בדיסקים שונים מה שעוזר לשרידות שלו, אבל עדיין יש את הסיכוי שהם יפלו. אז בנוסף לכך אחרי שמחלקים את המידע לdata shards, ניתן להגדיר כאלו נוספים שהם parity shards. בעקרון ככה אם חלק מהקבוצה הכוללת של הshards נופל, ניתן בעזרת תת קבוצה אחרת כנראה לשחזר אותם. יש כמה אלגוריתמים לעשות את זה, הפשוט ביותר זה עם פעולת XOR. בנוסף לכך, הmetadata נשמר במקום אחר, בDB, מה שגם הגיוני כי אנחנו לא תמיד נרצה לפנות למידע עצמו ולפעמים הmetadata מספיק אז כל עוד אפשרי לפנות בנפרד לmetadata שזעיר יותר עדיף לעשות את זה בצורה מופרדת. מבחינת כשלים וטעויות במידע, טעויות במידע יכולות לקרות בזמן תהליך השמירה גם תוכנתית וגם חומרתית. כדי למנוע דברים כאלו, משתמשים בchecksum שהוא פונקציה חח"ע כך שאם יש לי שינוי קטן לאור טעות כלשהי במידע הchecksum יהיה שונה וכך נדע שהייתה שגיאה איפשהו. ניתן להשתמש בCloudWatch כדי לקבל מטריקות על התנהגות חריגה כדי להבין שיש משהו בעייתי ומהם להבין איך לטפל. בשביל שרידות, שנותן לנו גם זמינות, חשוב שיהיה כמה שיותר שכבות שונות של ביזור. הביזור גם נותן לנו זמינות גדולה יותר כי זה לא יוצר bottleneck של פניות למקום מסוים אלא מחלק את זה בין אזורים שונים.



3. **Large Object Uploads and Client Workflow:** How does a client upload large objects to S3 using multipart upload, what are the typical 
part-size and file-size considerations, and how does this affect client workflow and performance?
A:
ברגיל פעולת PUT יכולה לשאת עד 5GB, אבל אם אתה מעלה בעזרת multipart אתה יכול עד 5TB. מומלץ להשתמש בmultipart בקבצים מעל 100MB. מבחינת הביצועים, התהליך הרבה יותר מהיר בזכות מקביליות. גם אפשר לעצור את התהליך באמצע בלי לאבד התקדמות במה שהצליח להעלות. מבחינת הflow, יש שלושה חלקים. אתה מאתחל את התהליך וS3 מחזיר לך ID. אתה מביא חלקים לתהליך עם ID, תוכן ומספר סידור. S3 מחזיר לך checksum על כך חלק שמסיים להעלות ואם מעלים חלק עם מספר סידורי שכבר קיים אז זה דורס אותו במקום. התהליך מסתיים כשנותנים את כלהchecksums מהשלב הקןדם. אם הכל תואם, אז התהליך הסתיים בהצלחה. 


4. **Lifecycle, Retention, and Governance:** Explain how a client can configure S3 Lifecycle rules to manage data retention, delete markers, and cleanup of incomplete multipart uploads, what are S3 Object Lock (WORM) policies and how they are used to manage cost, compliance, and long-term storage. How do these features support archival and recovery workflows?
A:

יש כמה דרכים בהן הלקוח יכול לקנפג את החוקים בS3 Lifecycle. אפשר להשתמש בAWS CLI, בS3 REST API ועוד. אפשר לקבוע שקבצים ימחקו אחרי זמן מסוים או יועברו למקום נפרד פחות נגיש עם אחסון יותר זול, סוג של archive ברעיון. כמובן שאפשר להגדיר חוקים חכמים יותר. חשוב להגיד שיש עיכוב בין הרגע שמזוהה שיש עמידה בקריטריונים של חוק עד הרגע שהפעולה יוצאת לפועל. בנוגע לObject lock policies, הרעיון הוא די פשוט. להפוך את מערכת האחסון לWORM, כלומר כתיבה אחת והמון קריאות. גם הפרק זמן שבוא ניתן לקרוא הוא מוגבל ואף אחד לא יכול לפעול אחרת. הגישה הזו מאוד טובה נגד תוקפים שינסו לפרוץ לנו לאחסון ולמחוק לנו את הגיבויים, בזכות הגישה הזו אנחנו מוגנים מסיטואציה כזו בכך שיש לנו אחסון שלא ישתנה, לא משנה מי אתה ואיזה הצלחות הצלחת להשיג (אם אנחנו שנייה במצב של Compliance). אם מישהו יפרוץ וימחק לנו, אז תמיד יהיה את הגיבוי הזה שנוכל לסמוך עליו. כן צריך לאזהר שאם אני עובד עם גרסאות, אז כשאני עושה overwrite זה יעשה גרסה חדשה וגם אותה ישמור לטווח הארוך, וזו חולשה שאפשר לנצל.
